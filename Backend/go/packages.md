# 6. Пакеты и модули

> Источники: [Спецификация — Packages, Program initialization](https://go.dev/ref/spec) · [Go Modules Reference](https://go.dev/ref/mod) · [Metanit — глава 6](https://metanit.com/go/tutorial/)

## Пакет

Все файлы одной папки принадлежат одному пакету. Имя в `package` — короткое, его пишут при вызове: `fmt.Println`.

Имя с заглавной буквы **экспортировано**: его видно при импорте. С маленькой — только внутри пакета.

```go
package greet

func Hello(name string) string { // видно снаружи
    return "Привет, " + name
}

func trim(s string) string { // только здесь
    return s
}
```

Импорт в другой папке:

```go
import "example.com/app/greet"

func main() {
    fmt.Println(greet.Hello("Анна"))
}
```

Путь в `import` — это путь модуля плюс каталоги, а не имя в строке `package`. Имя пакета и последний сегмент пути обычно совпадают, но это соглашение, а не правило.

Несколько импортов группируют скобками. Пакет можно вызвать другим именем:

```go
import (
    "fmt"
    myfmt "fmt"
    _ "image/png" // только ради побочного эффекта init, имя не используется
)
```

Пустой идентификатор `_` подключает пакет, чтобы выполнилась его функция `init` (так драйверы БД регистрируют себя), и при этом компилятор не ругается на неиспользуемое имя.

Циклический импорт запрещён: пакет A не может импортировать B, если B уже импортирует A.

## Инициализация

Порядок старта программы:

1. Импортированные пакеты инициализируются раньше текущего.
2. В пакете считаются константы и переменные уровня пакета.
3. Вызываются функции `init()` этого пакета (их может быть несколько, даже в разных файлах).
4. У программы `package main` затем вызывается `main`.

На порядок файлов в папке лучше не опираться. Общую подготовку держите в одном `init` или в обычной функции, которую вызывают явно.

## Модуль

Модуль — единица версий и зависимостей. Корень модуля — каталог с `go.mod`.

```bash
go mod init example.com/app
```

```text
module example.com/app

go 1.22
```

Каталоги внутри модуля — пакеты. Типичное начало:

```text
app/
├── go.mod
├── main.go          ← package main
└── internal/
    └── store/
        └── store.go ← package store, снаружи модуля не импортируется
```

Каталог `internal` особенный: его пакеты может импортировать только код **внутри** родительского дерева. Чужой модуль до `internal/store` не дотянется.

## Внешние зависимости

```bash
go get github.com/пример/пакет@latest
```

`go get` дописывает требование в `go.mod` и контрольные суммы в `go.sum`. Сборке нужны оба файла: `go.sum` проверяет, что скачанное не подменили.

`go mod tidy` приводит модуль к фактическим импортам: добавляет недостающие требования и удаляет неиспользуемые. Поднять версии к более новым — отдельный шаг, `go get пакет@latest` для конкретного модуля.

## vendor

`go mod vendor` копирует зависимости в папку `vendor/`. Сборка тогда может идти без сети: `go build -mod=vendor`. Так фиксируют точный набор исходников на CI или в поставке, где модульный прокси недоступен.

## Общий модуль

Код, который нужен двум сервисам, выносят в отдельный модуль со своим `go.mod` и подключают как обычную зависимость.

Пока модуль ещё не опубликован, его подключают с локального диска директивой `replace` в `go.mod` потребителя:

```text
require example.com/shared v0.0.0
replace example.com/shared => ../shared
```

Версия слева обязательна в `require`, даже если справа лежит папка. После публикации `replace` убирают и оставляют обычную версию.
